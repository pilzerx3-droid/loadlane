# ADR 0003: Auth hosted oidc

Status: Accepted. The product owner chose ZITADEL Cloud (US region) on 2026-11-27. Not yet verified against a live instance; this ADR is updated when that has been done.

## Decision so far

Use a hosted OIDC provider with organization and SSO support, behind our own interface so it can be swapped. Auth.js is not chosen because the API is a separate NestJS service. The comparison below was done in the P1-06 spike. The decision is **ZITADEL Cloud in its US region**, used only through standard OIDC, with no ZITADEL SDK.

## Where tenancy lives

Organizations, memberships and roles are our own data (ADR 0002, tables `organization`, `membership`, `membership_role`). The provider only has to prove who a person is: a stable `sub`, a verified e-mail address, MFA and enterprise SSO. So "organizations" in the provider is a nice-to-have, not a requirement, and a provider that allows one person in only one provider organization is acceptable. Never treat a provider claim as authorization; the API decides from our tables.

## Method and limits

Facts were read on 2026-11-27 from the providers' official pages only (docs, pricing, trust and legal pages), by delegated readers who reported the source URL for each fact. Anything not found is written as "not found" and must be treated as unknown, not as "no". Prices are as listed on that date, in USD where a currency was shown, and billing units differ between providers (MAU, MRU, DAU), so the totals cannot be compared directly. Nothing was tested against a live tenant yet.

## Assessment

- **Standard OIDC and exit path decide this.** Our requirement is a provider that can be swapped behind our own interface. Only ZITADEL documents the full standard protocol and a way to take password hashes with us. WorkOS needs a vendor-specific code exchange. Clerk's documented model is SDK based.
- **US region:** only ZITADEL documents a selectable US region. WorkOS and Clerk appear to be US-hosted, which is acceptable for a US-first launch but gives no EU option for later (ADR 0005).
- **Enterprise SSO:** WorkOS is built for it and has the clearest per-connection price, but each customer connection costs $65 to $125 per month. For ZITADEL the cost shows up as extra IdP slots ($100 each beyond three on Pro). Which costs fall on us and which on the customer is a commercial decision (see docs/us-market-notes.md).
- **Risks of ZITADEL:** AGPL-3.0 for the server (no obligation while we only use the hosted service through standard OIDC; self-hosting or modifying it needs a license decision under CLAUDE.md), a smaller ecosystem than the other two, SMS needs Twilio, unclear DAU billing unit, and one provider organization per user (handled by keeping tenancy in our database).
- **Why not WorkOS now:** AuthKit is not a plain OIDC provider, no export of hashes, and the open security investigation at the vendor. It remains the strongest option if enterprise SSO sales become the main driver; because of our interface, switching later is possible.
- **Why not Clerk now:** the standard-OIDC role could not be found in the official docs, and data residency is "Not offered".

## Consequences for the implementation (Part 2 of P1-06)

- Our own interface `TokenVerifier` verifies access tokens with a generic JWT library. It checks issuer, audience (our own client id or API identifier, because not every provider sets `aud`), expiry, signature and an algorithm allowlist.
- Verified e-mail is read from the standard userinfo endpoint on first sign-in, never assumed. A person whose e-mail is not verified is refused (403, code `email_not_verified`).
- A person is identified only by `(issuer, subject)`. Linking accounts by e-mail address is not automatic (account takeover risk); a second identity with a known e-mail gets 409 (`email_in_use`).
- With ZITADEL, the access token type must be set to JWT for the application; to be confirmed against a real test instance.
- The browser flow is Authorization Code with PKCE as a public client (no client secret). Sessions live server-side in Valkey; the browser holds an opaque id in an HttpOnly cookie.
- Looking up and registering people before their id is known needs a narrow database policy (migration 0003, ADR 0002).

## Implementation status (P1-06)

- Built: `TokenVerifier` with a jose implementation, discovery and key set handling, first-sign-in registration, `GET /v1/me`, web login, callback, logout, session renewal.
- Tested against a local stand-in for the provider and the real database (see docs/dev-setup-zitadel.md, "What was tested").
- **Not yet verified against a live ZITADEL instance.** Open items to confirm there: access tokens are JWTs, `aud` contains the project id, userinfo returns `email_verified`, the end-session redirect works. This section is updated when someone has signed in once.

## Open questions

- Commercial: who pays for enterprise SSO connections.
- Legal: processing agreement with the chosen provider and the retention of authentication logs (see ADR 0002).
- First-sign-in registration is not written to `audit_log`, because that table requires an organization and a new person has none yet. A platform-level audit trail is needed before launch.
- Refresh tokens that rotate can fail when two requests refresh in parallel. The web app falls back to tokens another request stored, but a stricter lock may be needed under load.
